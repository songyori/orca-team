# orca-team 문구 규칙 설계

- 날짜: 2026-11-05
- 대상: orca-team 0.4.1(`orca-team/`). 선행 설계는 `2026-10-30-orca-team-design.md`, `2026-10-31-orca-team-design-director-design.md`이다.
- 상태: 사용자가 브레인스토밍 결정 5개와 설계 1–4절을 승인했다.

## 1. 목적

개발 중에 만드는 한국어 텍스트(서비스 내 문구, 정책·법률 문서, 사용자용 문서)를 같은 규칙으로 쓰고 같은 규칙으로 리뷰한다.

1. 작성하는 Claude 직무 워커와 리뷰하는 Codex가 규칙 파일 하나를 함께 기준으로 쓴다.
2. 규칙은 두 공개 한국어 윤문 스킬에서 개발 텍스트에 필요한 부분만 가져와 압축하고, 두 스킬에 없는 UI 문구 규칙을 더한다.
   - `amondnet/yoonmoon`(MIT): 교정·교열, 문체·높임 체계, AI 티 분류, 과소 서술(삭제 과교정) 가드
   - `epoko77-ai/im-not-ai`(MIT): 서법(의무·가능성·완곡) 보존, 실측으로 확인된 AI 신호("A가 아니라 B" 대구, 연결어미 뒤 쉼표), 실측으로 기각된 과교정("~를 통해"·"것이다" 무조건 교정)
3. 프로젝트마다 문체와 용어를 기획 단계에서 정하고, 작성·리뷰·자동 검사가 그 기준과 대조한다.
4. 기계적으로 찾을 수 있는 오류(확정 오탈자, 이중피동, 금지 표기 등)는 orch 자동 검사가 의심 위치로 리뷰에 넘긴다.

### 1.1 두 스킬을 그대로 쓰지 않는 이유

2026-11-05에 두 스킬을 같은 AI 글 3편에 지침대로 돌리고 블라인드 심사 2회로 비교했다. 선호는 3대 3이었고, im-not-ai는 의미 보존(평균 8.3 대 7.2), yoonmoon은 AI 티 제거(6.7 대 5.8)에서 앞섰다. 개발 텍스트 리뷰에 그대로 쓰기 어려운 이유는 다음과 같다.

- 둘 다 글을 다시 쓰는 도구다. orca-team 리뷰어는 `REVIEW_FILE` 하나에 `파일:줄 — 문제` 지적만 쓴다.
- im-not-ai의 기준선과 처방은 긴 산문(에세이·칼럼·리포트·블로그·초록) 기준이다. 장문 결핍을 메우라는 처방(E-1)은 UI 문구와 기술 문서에 맞지 않는다. 맞춤법 교정은 범위 밖이라고 명시한다.
- yoonmoon은 "A가 아니라 B" 대구 패턴이 없고, 사람 글이 더 많이 쓰는 표현("~을 통해", 직역 대명사)을 AI 티로 다뤄 과교정 위험이 있다. 정책 문서에서 중요한 서법 보존이 약하다(실측에서 추측을 단정으로 바꿨다).
- 둘 다 용어 통일, i18n 변수 보존, 버튼·오류 메시지 규칙이 없다.

## 4. 규칙 파일 (`templates/text-rules.md` → `.orchestration/text-rules.md`)

80–100줄을 목표로 한다. 절마다 출처를 둔다(Y = yoonmoon, I = im-not-ai, O = orca-team).

### 4.1 §0 범위
서비스 내 문구(UI 라벨·버튼·오류·알림·빈 화면 문구), 정책·법률 문서, 사용자용 문서(README, 도움말, 가이드, 릴리스 노트)의 한국어 텍스트에 적용한다. 기획 문서, 워커 리포트, 리뷰 파일에는 적용하지 않는다.

### 4.2 §1 보존 — 다른 모든 규칙보다 우선 (I+Y)
- 고유명사, 수치·단위·날짜·금액, 코드·키·URL·식별자를 바꾸지 않는다.
- i18n 변수(`{name}`, `%s`, `{{count}}`, `%(name)s`)와 HTML·JSX 태그를 보존한다. 변수의 개수와 이름이 같아야 한다.
- 정책 문서의 의무·권한·가능성·금지 표현("~하여야 한다·하여야 합니다", "~할 수 있다·할 수 있습니다", "~할 수 있을 것으로", "~하지 않는다·하지 않습니다")은 의미를 바꾸지 않는다. §4의 hedging 규칙보다 우선한다.
- 주장의 방향·강도·인과를 바꾸지 않는다. 덜어내다가 문장 성분·필수 조사·어미가 빠져 뜻이 흐려지면 되돌린다.

### 4.3 §2 맞춤법·표기 (Y proofread)
- 맞춤법, 띄어쓰기(의존명사 "수·것·때·데", 보조용언, 단위 명사), 표준어, 외래어 표기법, 문장부호(접속어 뒤 쉼표를 쓰지 않는다 등).
- 확정 오류는 고친다. 규범 판단이 갈리는 것(예: 보조용언 붙여쓰기 허용)은 고치지 않고 리뷰에서 P3로만 적는다.

### 4.4 §3 문체·용어 일관성 (Y restyle + O)
- `docs/planning/voice.md`의 문체(종결체), 호칭, 라벨 형태, 용어집을 따른다. voice.md가 없으면 한 화면·한 문서 안에서 종결체와 용어 표기를 섞지 않는 것만 지킨다.
- 높임 정합: 주체 높임("-시-")과 상대 높임(종결체)을 한 문장 안에서 어긋나게 쓰지 않는다.
- 버튼·메뉴 라벨은 voice.md가 정한 한 형태로 쓴다("저장"과 "저장하기"를 섞지 않는다).
- 오류 메시지는 무엇이 잘못됐는지와 사용자가 할 일을 함께 쓴다. 사용자를 탓하는 표현("잘못 입력하셨습니다")과 내부 용어(예외 이름, 코드값)를 그대로 노출하지 않는다.

### 4.5 §4 AI 티·번역투 (Y 분류, I 실측으로 보정)
- **항상 고친다**
  - 상투어·과장어: 혁신적, 획기적, 최적의, 극대화, 차세대, 시너지, 패러다임, "Seamless", "Unlock", "Elevate"류
  - 챗봇 잔재: "도움이 되셨길 바랍니다", "궁금한 점이 있으시면 언제든", "물론입니다"
  - 메타 hedging: "~라고 할 수 있다", "~다고 볼 수 있다", "~것으로 보여진다". 정책 문서의 권한·가능성 표현은 §1이 우선한다
  - 이중피동("되어지다", "보여지다"), "~에 있어서"
  - 문두 접속어("그리고", "또한", "그러나", "따라서", "하지만") 뒤 쉼표
  - "A가 아니라 B" 대구가 한 화면·한 문서에 2회 이상(가장 나은 1회만 남긴다)
  - 영어 병기 남발: 첫 등장 1회만, 용어집이 병기를 정한 용어만
- **반복될 때만 고친다** (한 문서·한 화면에 3회 이상): "~를 통해", "~에 대해", 형식명사 "것", 무생물 복수 "-들", 문두 "또한/따라서", "~중 하나", 연결어미("-며", "-고", "-지만", "-면서", "-아서/-어서") 직후 쉼표(긴 문장을 끊어 읽어야 하면 남긴다)
- **고치지 않는다** (과교정 방지)
  - "~를 통해", "것이다"가 1–2회 쓰인 경우. 실측에서 사람 글이 더 많이 쓴다(I)
  - 가이드·문서의 열거 표지(첫째/둘째, 번호 목록)
  - 짧은 문장. UI 문구와 기술 문서에서 짧은 문장을 장문으로 잇지 않는다
  - 덜어내다가 의미가 모자라게 되는 경우: 성분 생략, 개조식 종결, 비유 어휘 대치(Y 11번)

### 4.6 §5 리뷰 심각도 (O)
- **P1** (반려): 정책 문서의 의무·권한·책임 표현 오류나 변경, i18n 변수·태그 손상, spec과 다른 사실·수치, 사용자에게 보이는 확정 맞춤법 오류
- **P2**: voice.md 문체·용어 위반, 한 화면 안의 높임법 섞임, 할 일을 알려 주지 않는 오류 메시지, §4 "항상 고친다" 항목
- **P3**: §4 "반복될 때만" 항목, 판단이 갈리는 교정, 더 나은 표현 제안, 이 태스크가 바꾸지 않은 기존 텍스트의 문제

### 4.7 출처
파일 끝에 두 저장소 URL과 MIT 라이선스, 가져온 범위(4.2–4.5의 출처 표시)를 적는다. 원문을 복사하지 않고 규칙을 새로 압축해 쓴다.

## 5. 문구 기준 (`docs/planning/voice.md`)

### 5.1 planner (`templates/roles/planner.md`)
- 점검표에 "문구 기준(서비스 문구·정책 문서·사용자 문서의 문체, 사용자 호칭, 버튼·메뉴 라벨 형태, 핵심 용어 표기)"을 추가한다.
- 문체는 질문 1개로 추천안과 함께 묻는다. 추천 기본값은 서비스 문구 해요체, 정책 문서 하십시오체, 사용자 문서 해요체, 호칭 생략, 라벨 명사형이다. 서비스 성격상 자명하면 묻지 않고 "자동 결정"으로 표시한다.
- 용어집은 spec의 기능·화면·데이터 이름에서 planner가 뽑는다. 따로 묻지 않고 확정 질문의 요약(`context`)에 넣어 함께 승인받는다.
- 확정 산출물은 네 개에서 다섯 개가 된다(`voice.md` 추가). 증분 기획이면 기존 voice.md를 읽고 바뀌는 부분만 고친다.
- voice.md는 planner만 고친다(소유 경로 `docs/planning/**`).

### 5.2 형식
자동 검사가 읽으므로 절 제목과 용어집 표 머리를 고정한다.

```markdown
# 문구 기준

## 문체
- 서비스 문구: 해요체
- 정책 문서: 하십시오체
- 사용자 문서: 해요체
- 호칭: 생략. 필요하면 "회원님"

## 라벨
- 버튼·메뉴: 명사형("저장", "삭제")

## 용어집
| 쓰는 표기 | 쓰지 않는 표기 | 메모 |
|---|---|---|
| 로그인 | 로그 인, 로긴 | |
| 회원가입 | 회원 가입 | |
```

- 용어집은 `## 용어집` 절의 첫 표만 읽는다. "쓰지 않는 표기" 칸은 쉼표로 나눈다. 빈 칸이면 그 행은 검사하지 않는다. 괄호 조건이 붙은 표기("지우기(라벨)")는 조건을 평가할 수 없어 검사하지 않는다.
- 형식이 틀려 읽을 수 없으면 용어집 검사만 건너뛴다(오류로 멈추지 않는다).

## 6. 작성 경로 (Claude 직무 워커)

### 6.1 designer·developer (`templates/roles/designer.md`, `templates/roles/developer.md`)
- 입력에 `.orchestration/text-rules.md`와 `docs/planning/voice.md`(있으면)를 추가한다.
- 서비스 문구나 사용자용·정책 문서를 쓰거나 바꾼 태스크는 `.orchestration/text-rules.md`를 지키고, 리포트 현재 라운드 `## r{round}` 절 안에 `### 문구 점검` 소절을 둔다. 내용은 §1–§4를 지켰는지, 예외와 근거, 용어집에 없는 새 핵심 용어 목록이다.
- director, tester, planner는 대상이 아니다(산출물이 내부 문서다). planner는 voice.md만 쓴다.

### 6.2 소유 경로 (`templates/config.toml`)
- developer `owns`에 `README.md`, `docs/user/**`, `docs/policy/**`를 추가한다. 지금은 이 경로를 맡는 직무가 없다.
- 기존 프로젝트의 `.orchestration/config.toml`은 바꾸지 않는다(9절).

### 6.3 위치 안내 (`templates/CLAUDE.section.md`)
"위치"에 `.orchestration/text-rules.md`(문구 규칙)와 `docs/planning/voice.md`(문구 기준) 줄을 추가한다.

## 7. 리뷰 경로 (Codex)

### 7.1 리뷰 절 (`templates/review-text.md`)
`review-design.md`처럼 리뷰 프롬프트에 끼워 넣는 절이다. 디자인 절이 없을 때도 번호가 어긋나지 않게 번호 없는 글머리로 쓴다.

```markdown
## 문구 기준
- 이 태스크가 바꾼 서비스 문구·정책 문서·사용자 문서를 `.orchestration/text-rules.md` 와 `docs/planning/voice.md`(있으면)로 본다. 심각도는 text-rules §5 를 따른다. P1 은 REQUEST_CHANGES 사유다.
- 이 태스크가 바꾼 텍스트만 지적한다. 원래 있던 문제는 P3 로만 적는다.
- 워커 직무 정의(`.orchestration/roles/<직무>.md`)가 `### 문구 점검` 을 요구하면, 리포트 마지막 라운드에 그 소절이 있는지와 실제와 맞는지 본다.

orch 문구 자동 검사(이 태스크가 추가한 줄의 의심 위치. 정당한 쓰임도 있으니 직접 열어 보고 판단한다):
{text_lint}
```

### 7.2 붙는 조건 (`lib/orch/review.py` `text_section()`)
다음 둘을 모두 만족하면 붙인다. 직무와 무관하다.

1. 프로젝트에 `.orchestration/text-rules.md`가 있다(0.5.0 이후 설치). 없으면 빈 문자열(이전 버전 호환).
2. 태스크가 바꾼 파일 중 텍스트 대상이 하나 이상 있다. 텍스트 대상은 다음을 모두 만족하는 파일이다.
   - 확장자: `.md`, `.mdx`, `.txt`, `.html`, `.htm`, `.js`, `.jsx`, `.ts`, `.tsx`, `.vue`, `.svelte`, `.json`, `.yaml`, `.yml`, `.po`, 모바일 문구 파일 `.arb`, `.dart`, `.strings`, `.xcstrings`, `.xml`, `.kt`, `.swift`(웹·Flutter·iOS·Android)
   - 제외 경로가 아니다: `docs/planning/**`, `docs/tasks/**`, `docs/reviews/**`, `docs/qa/**`, `docs/design/*.md`, `docs/design/board/**`, `docs/design/pilots/**`, `docs/design/system/**`, `tests/**`, `.orchestration/**`, `**/*.test.*`, `**/*.spec.*`, `**/__tests__/**`, `e2e/**`
   - 검사 대상 줄(코드 주석 줄, Markdown 코드 블록·인라인 코드 제외)에 한글 음절(U+AC00–U+D7A3)이 하나 이상 있다. 1MB 초과·UTF-8 아님·없음이면 대상이 아니다.

`templates/review-prompt.md`는 `{design_section}{text_section}## REVIEW_FILE 형식` 순서로 자리를 둔다. `text_section`도 `design_section`처럼 다음 절과 사이의 빈 줄까지 붙여 돌려준다.

### 7.3 Codex 리뷰 파일
Codex가 쓰는 리뷰 파일 문장에는 이 규칙을 적용하지 않는다(결정 2). `templates/AGENTS.md`는 바꾸지 않는다.

## 8. 자동 검사 (`lib/orch/textlint.py`)

`lib/orch/lint.py`(디자인 검사)는 바꾸지 않고 새 모듈을 둔다. 결과는 의심 위치일 뿐 자동 불합격이 아니다.

### 8.1 검사할 줄
- 태스크 커밋마다 `git show --format= -U0 <sha> -- <파일>`의 `+` 줄(`+++` 제외)을 모은다.
- 지금 파일에서 내용이 그 집합에 있는 줄만 현재 줄 번호로 검사한다. 같은 체크아웃의 다른 워커 변경과 기존 텍스트는 잡지 않는다.
- git 오류가 나면 그 파일은 건너뛴다(리뷰 절은 그대로 붙는다).

### 8.2 건너뛰는 부분
- 코드 확장자(`.js`, `.jsx`, `.ts`, `.tsx`, `.vue`, `.svelte`, `.yaml`, `.yml`, `.dart`, `.kt`, `.swift`, `.strings`)에서 앞 공백을 뺀 줄이 `//`, `/*`, `*`, `#`로 시작하는 줄
- `.html`, `.htm`, `.xml`에서 앞 공백을 뺀 줄이 `<!--`로 시작하는 줄
- Markdown(`.md`, `.mdx`)의 펜스 코드 블록(```` ``` ````, `~~~`) 안 줄, 그리고 줄 안의 인라인 코드(백틱 구간)
- 한글이 없는 줄

### 8.3 검사 항목

| 분류 | 찾는 것 |
|---|---|
| 확정 오탈자 | 됬, 몇일, 어떻해, 금새, 왠만, 오랫만, 역활, 희안, 설겆이, 할께, 일일히, 깨끗히, 틈틈히, 되요, 안되요 |
| 이중피동 | 되어지·되어진·되어짐·되어져·되어졌, 보여지·보여진, 쓰여지·쓰여진, 불려지·불려진 |
| 번역투 | "에 있어서", "에 있어 " |
| 상투어 | 혁신적, 획기적, 최적의, 극대화, 차세대, 시너지, 패러다임, 게임 체인저, seamless, empower (영문은 대소문자 무시) |
| 메타 hedging | "라고 할 수 있", "다고 볼 수 있", "것으로 보여지", "것으로 보인다고" |
| 챗봇 잔재 | "도움이 되셨길", "도움이 되었길", "도움이 되셨으면", "궁금한 점이 있으시면 언제든", "물론입니다" |
| 쉼표 | 한글 연결어미 "며·지만·면서·아서·어서·여서·해서" 바로 뒤 쉼표, 하·되·있·없·않·이·었·았·했·겠 뒤의 "고,", 줄·문장 첫머리 접속어 "그리고·또한·그러나·따라서·하지만" 뒤 쉼표 |
| 금지 표기 | voice.md 용어집 "쓰지 않는 표기". 같은 자리를 "쓰는 표기"가 덮으면 건너뛴다(금지 "가입"이 "회원가입" 안에 있는 경우) |
| 높임법 섞임 | 한 파일의 검사 줄에 해요체 종결("요"로 끝남)과 하십시오체 종결("니다·니까·십시오"로 끝남)이 모두 있으면 1건. 적은 쪽 줄 번호를 최대 5개 적는다. 종결 판정은 뒤의 따옴표·문장부호·공백을 뺀 뒤 한다. 해요체 예외: 필요·중요·개요·주요·수요·아니요·좋아요 |

- 정책 문서의 "할 수 있다"는 검사하지 않는다. hedging은 메타 표현만 잡는다.
- 이모지는 디자인 검사(`lint.py`)가 이미 잡으므로 넣지 않는다.

### 8.4 출력
- `파일:줄: 분류(발췌)` 목록을 파일 순서·줄 순서로 돌려준다. 발췌는 60자.
- 최대 50건. 넘으면 마지막 항목이 `… 외 N건`이다. 없으면 `- 없음`.

## 9. 업그레이드

- 새 프로젝트: init이 `text-rules.md`를 설치하고, planner·designer·developer 정의와 config가 새 규칙을 담는다.
- 기존 프로젝트: init을 다시 실행하면 `.orchestration/text-rules.md`만 새로 생긴다. 그때부터 Codex 리뷰에 문구 절이 붙는다. 직무 정의·config는 덮어쓰지 않으므로 워커가 규칙을 작성에 쓰게 하려면 사용자가 직접 바꾼다. voice.md가 없으면 용어집 검사는 건너뛴다.
- README의 업그레이드 안내에 이 내용을 적는다.

## 10. 오류 처리

| 상황 | 처리 |
|---|---|
| text-rules.md 없음 | 문구 절을 붙이지 않는다 |
| voice.md 없음·형식 오류 | 용어집 검사만 건너뛴다 |
| git show 실패 | 그 파일의 자동 검사를 건너뛴다. 절은 붙인다 |
| 대상 파일 1MB 초과·UTF-8 아님·삭제됨 | 텍스트 대상이 아니다 |
| 자동 검사 중 예외 | 그 내용을 한 줄 "자동 검사 실패: …" 로 적고 절은 붙인다 |
| 의심 위치 50건 초과 | 50건 + `… 외 N건` |
