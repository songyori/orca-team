# orca-team 디자인 규칙 설계

- 날짜: 2026-11-06
- 대상: orca-team 0.5.1(`orca-team/`). 선행 설계는 `2026-10-31-orca-team-design-director-design.md`(디자인 디렉터·금지 목록), `2026-11-05-orca-team-text-rules-design.md`(문구 규칙)이다.
- 상태: 사용자가 브레인스토밍 결정 2개, 설계 1–3절, 버전 0.5.2 를 승인했다.

## 1. 목적

디자인·UI 작업의 품질 기준을 "하지 말 것"에서 "이렇게 하라"까지 넓히고, Codex 리뷰가 태스크가 바꾼 것만 근거를 대며 판정하게 한다.

1. 지금 `design-rules.md` 는 AI 티 금지 목록 10개뿐이다. 접근성, 색, 글자, 레이아웃, 표면·동작, 상태에 대한 긍정 규칙을 더한다.
2. 지금 `review-design.md` 는 기준 두 줄뿐이다. 변경분 분류(새로 생김·회귀·기존), 지운 줄 읽기, 빠진 상태 찾기, 즉시 차단 항목, 싼 수정 순서, 근거 요구를 더한다.
3. 기계적으로 찾을 수 있는 회귀(지운 줄에서 줄어든 접근성 신호)와 차단 항목(확대 막기, 대체 없는 포커스 제거)은 orch 자동 검사가 의심 위치로 리뷰에 넘긴다.
4. 작성하는 Claude 직무 워커(director, designer, developer)와 리뷰하는 Codex 가 같은 규칙 파일을 기준으로 쓴다.

### 1.1 원본을 그대로 쓰지 않는 이유

규칙은 jakubkrehel/skills(https://github.com/jakubkrehel/skills, MIT, 2026-11-01 커밋 60bf140 기준)에서 가져온다. 플러그인을 그대로 설치하지 않는 이유는 다음과 같다.

- 스킬 15개, 마크다운 약 36만 바이트다. 워커가 태스크마다 읽기에 크고, 리뷰어가 같은 기준을 쓰게 연결하기 어렵다.
- 리뷰 형식(심각도 HIGH·MEDIUM·LOW, 15개 상한 표, Approve 판정)이 orca-team 리뷰 파일 형식(`[P1|P2|P3] 파일:줄`, `VERDICT:`)과 다르다.
- 한국어(CJK) 내용이 없다. 앱 플랫폼(iOS·Android·Flutter) 내용이 없다.
- Codex 쪽에도 따로 설치해야 한다.

## 4. 규칙 파일 (`templates/design-rules.md` → `.orchestration/design-rules.md`)

제목을 "디자인 규칙"으로 바꾼다. 첫머리는 다음을 말한다.

- 디자인 디렉터(director), 화면 디자이너(designer), 개발자(developer)의 UI 작업이 지키고, Codex 리뷰도 이 규칙으로 판정한다.
- UI 를 바꾼 태스크는 리포트 현재 라운드 `## r{round}` 절 안의 `### 디자인 점검` 소절에 다음을 적는다.
  - §1 항목마다 지켰는지
  - §2–§6 에서 어긴 곳과 예외·근거(지킨 항목은 늘어놓지 않는다)
  - §7 에서 확인한 상태와 확인 방법
- `orch review` 는 기계적으로 찾을 수 있는 의심 위치를 리뷰 프롬프트에 넣는다. 판정은 Codex 가 한다.

### 4.1 §0 범위
- 값은 웹(CSS) 기준이다. 앱(iOS·Android·Flutter)은 같은 원칙을 플랫폼 기능으로 지킨다: 접근성 라벨(`accessibilityLabel`·`contentDescription`·`Semantics`), 글자 크기 설정(Dynamic Type·글꼴 배율), 동작 줄이기 설정, 터치 영역 44pt(iOS)·48dp(Android).
- 프로젝트 디자인 시스템(`docs/design/system/`)이 정한 값이 먼저다. 시스템에 없는 값이 필요하면 designer 는 `### 시스템 추가 제안` 에 적고, developer 는 ask 로 묻는다. director 는 시스템을 만들 때 이 규칙을 반영한다.
- 밀도, 모서리 크기, 말투처럼 시스템이 일관되게 정한 취향은 위반이 아니다. 한 프로젝트 안에서 같은 것을 두 방식으로 하면 위반이다.

### 4.2 §1 금지 목록 (AI 티)
지금 1–10번을 그대로 옮긴다. 문장은 바꾸지 않는다.

### 4.3 §2 접근성 (WCAG 2.2 AA)
1. 네이티브 요소를 먼저 쓴다. 동작은 `<button>`, 이동은 `<a href>` 이고 `<div onClick>` 을 쓰지 않는다. 네이티브 요소가 있으면 ARIA 로 흉내 내지 않는다.
2. 포커스 표시는 `:focus-visible` 에 둔다. 대체 표시 없이 `outline: none` 을 쓰지 않는다. 직접 만든 포커스 링은 맞닿는 색과 3:1 이상이다.
3. 포인터로 하는 모든 조작을 키보드로도 할 수 있다. Esc 는 겹친 창을 닫고, Tab 은 위젯 사이를, 화살표는 위젯 안을 움직이고, Enter·Space 가 버튼을 누른다. `tabindex` 는 `0` 과 `-1` 만 쓴다.
4. 모달은 `<dialog>` 와 `showModal()` 을 먼저 쓴다. 열면 포커스를 안으로 옮기고 닫으면 연 컨트롤로 돌려준다. 클라이언트 라우팅으로 화면이 바뀌면 문서 제목을 바꾸고 새 화면의 `<h1>` 이나 `<main>` 으로 포커스를 옮긴다.
5. 누를 수 있는 영역은 24×24px 이상이다. 터치 화면은 44×44px, 데스크톱은 40×40px 를 목표로 한다. 보이는 크기를 키울 수 없으면 가상 요소로 영역을 넓히되 이웃 영역과 겹치지 않는다. 끌기 조작에는 버튼이나 메뉴 같은 대안을 둔다.
6. 모든 입력란에 보이는 라벨(`<label for>`)을 둔다. 자리표시(placeholder)는 라벨이 아니다. 알맞은 `type`·`inputmode`·`autocomplete` 를 쓰고 붙여넣기를 막지 않는다.
7. 오류는 제출할 때 검사한다. 유효할 때까지 제출 버튼을 비활성화하지 않는다. 틀린 칸에 `aria-invalid="true"` 와 오류 문구를 가리키는 `aria-describedby` 를 두고, 첫 틀린 칸으로 포커스를 옮긴다.
8. 아이콘만 있는 버튼에 `aria-label` 을 둔다. 보이는 라벨 글자는 접근 가능한 이름에 들어간다. 장식 요소는 `aria-hidden="true"` 로 숨기되 포커스를 받는 요소에는 쓰지 않는다. 이미지 대체 텍스트는 목적에 따라 쓴다: 장식은 `alt=""`, 정보 이미지는 뜻, 기능 이미지는 동작.
9. 상태를 색만으로 알리지 않는다. 아이콘·글자·밑줄을 함께 쓴다.
10. 움직임은 `@media (prefers-reduced-motion: no-preference)` 안에서만 쓴다. 동작 줄이기 설정에서는 이동·확대를 투명도 전환으로 바꾸고 시차 효과(parallax)와 자동 재생을 끈다.
11. 5초 넘게 스스로 움직이거나 바뀌는 것에는 멈춤 컨트롤을 둔다. 동작 버튼이나 오류가 든 토스트는 사용자가 닫을 때까지 남긴다.
12. 화면 갱신을 알린다. 입력란 검증은 `aria-describedby`, 급하지 않은 알림(토스트·결과 수)은 `role="status"`, 급한 오류만 `role="alert"` 로 알린다.
13. 제목은 문서 개요를 이루고, 화면마다 `<main>` 을 하나 둔다. 반복 내비게이션이 본문 앞에 있으면 "본문 바로가기" 링크를 첫 포커스 요소로 둔다. 문서에 `lang="ko"` 를 둔다.
14. 글자 200% 확대와 320px 폭에서 가로 스크롤 없이 내용과 컨트롤이 다 보인다. 뷰포트 메타에 `maximum-scale=1`·`user-scalable=no` 를 쓰지 않는다.

### 4.4 §3 색
1. 램프는 중립 하나, 강조 하나, 실제로 화면에 쓰는 상태(성공·경고·위험 등)만 둔다. 둘째 강조색은 두 대상을 한눈에 구별해야 할 때만 둔다.
2. 램프의 단계마다 역할이 있다(페이지 배경, 컴포넌트 hover, 테두리, 채움, 본문 글자). 쓰는 역할이 없는 단계를 만들지 않는다. 램프는 한 색상(hue)을 유지하고 눈대중이 아니라 색 도구로 만든다.
3. 기본 토큰은 색 이름(`blue-600`), 의미 토큰은 역할 이름(`color-text-secondary`)으로 짓는다. 컴포넌트는 의미 토큰만 쓴다.
4. 토큰은 그 역할에만 쓴다. 지금 값이 맞다고 테두리 토큰을 글자색으로 빌리지 않는다. 역할에 맞는 토큰이 없으면 시스템 추가 제안을 한다.
5. 한 색은 인터페이스 전체에서 한 뜻만 가진다. 위험 색을 일반 동작에 쓰지 않는다.
6. 색을 채운 주 버튼은 화면에 하나다. 동급의 다른 동작은 중립으로 둔다. 강조색은 글자가 아니라 배경에 둔다.
7. 대비는 그 글자가 실제로 렌더되는 배경과 잰다(페이지 배경이 아니다). 본문 4.5:1, 24px 이상(굵게 18.67px 이상) 글자 3:1, 컴포넌트 경계·상태·의미 있는 그래픽 3:1 이다. 비활성 컨트롤과 로고는 예외다. 대비가 모자라면 색 쌍, 측정값, 기준을 함께 적는다.

### 4.5 §4 글자
1. 글꼴은 3개 이하로 쓴다. 크기 단계는 적게 두고, 단계마다 줄간격·굵기를 묶어 쓰임 이름(`text-body-sm`)을 붙인다. 제목 크기는 단계가 내려갈수록 작아지고 본문보다 작지 않다.
2. 쓰는 굵기와 스타일의 글꼴 파일을 모두 불러온다(브라우저가 굵기를 합성하지 않게). 한글 웹폰트는 서브셋이나 동적 서브셋으로 불러오고 `font-display: swap` 을 쓴다.
3. 줄간격은 단위 없는 값으로 쓴다. 큰 표시 글자 1.1, 제목 1.2–1.3, 본문 1.5–1.6 이다. 세 줄 넘게 감기는 글은 1.4 이상이다.
4. 글자 간격은 `em` 으로 쓴다. 24px 이상 제목은 `-0.01em`–`-0.02em`, 14px 이하 대문자 라벨은 `0.05em`, 본문은 0 이다.
5. 크기 하한은 긴 본문 16px, 입력·메뉴 14px, 캡션 13px 이다. 12px 미만은 쓰지 않는다. 단위는 `rem` 이다. 18px 미만 글자는 굵기 400 이상이다. 모바일 입력란 글자는 16px 이상이다(iOS 화면 확대 방지).
6. 한글 본문과 제목은 어절 단위로 줄을 바꾼다(`word-break: keep-all`). 긴 URL·ID 가 넘칠 수 있는 곳에는 `overflow-wrap: break-word` 를 함께 둔다. 제목·짧은 설명은 `text-wrap: balance`, 문단은 `text-wrap: pretty` 를 쓴다. 정렬은 `text-align: start` 이고 양쪽 정렬을 쓰지 않는다. 긴 본문은 줄 길이 상한(`max-width`)을 둔다.
7. 한글에는 기울임을 쓰지 않는다. 한글 글꼴에는 기울임체가 없어 기울여 합성된다. 강조는 굵기나 색으로 한다.
8. 타이머·카운터·가격·표의 숫자 열은 `font-variant-numeric: tabular-nums` 를 쓴다. 문장 속 숫자는 그대로 둔다.
9. 말줄임으로 자른 글에는 전체를 볼 방법(펼치기, 상세 화면, 키보드로도 닿는 툴팁)을 둔다.
10. 쓸모 있는 글은 선택할 수 있게 둔다. `user-select: none` 은 끌기 표면에만 쓴다.

### 4.6 §5 레이아웃
1. 여백으로 먼저 묶고, 그다음 배경 면, 구분선은 마지막에 쓴다. 묶음 사이 간격은 묶음 안 간격의 2배 이상이다(안이 8px 이면 사이는 16px 이상).
2. 정렬 기준선을 몇 개로 정하고 모두 거기에 맞춘다. 중첩 단계마다 시스템 간격 한 단계를 쓴다.
3. 중요한 내용을 위와 시작 쪽에 둔다. 한 줄 안에서는 식별 내용이 앞, 메타 정보와 동작이 뒤다. 보이는 순서와 DOM 순서를 같게 둔다(`order`·`row-reverse` 로 바꾸지 않는다).
4. 화면마다 주 동작은 하나다. 보조 동작이 3개를 넘으면 메뉴로 묶는다.
5. 컨트롤은 배경 면·테두리·밑줄·고정 자리(도구 막대)로 본문 글과 구별한다.
6. 화면 밖이나 접힌 내용에는 보이는 단서를 둔다(다음 항목이 스크롤 끝에서 16–32px 보이게, 펼치기 컨트롤).
7. 테두리 없는 글자·아이콘 버튼 사이는 24px, 테두리나 채움이 있는 컨트롤 사이는 12px 에서 시작한다. 시스템 밀도가 있으면 그것을 따른다. 누르는 영역은 겹치지 않는다.
8. 배경과 미디어는 화면 끝까지, 컨트롤과 글은 레이아웃 여백과 안전 영역 안에 둔다. 모바일 전체 폭 버튼은 좌우 16px 안쪽에 둔다. 고정 헤더가 있으면 `scroll-padding-block-start` 를 그 높이로 둔다.
9. 글이 담기는 상자는 고정 폭·높이 대신 `max-width`·`min-height` 를 쓰고 줄이 감기게 둔다. 중요한 동작을 확대나 스크롤로 잘리는 곳에 두지 않는다.
10. 브레이크포인트는 기기 크기가 아니라 내용이 깨지는 지점에서 정한다. 가장 작은 폭과 가장 큰 폭을 먼저 확인한다.

### 4.7 §6 표면·동작
1. 겹친 면이 고른 안쪽 여백을 가지면 바깥 모서리는 안쪽 모서리 + 여백 + 테두리 두께다. 여백이 24px 를 넘거나 일부러 고르지 않으면 각자 모서리 토큰을 쓴다.
2. 높이감은 그림자로, 구조(구분선·표·선택 상태·입력란 경계)는 테두리로 나타낸다.
3. 상호작용 상태 변화는 keyframes 가 아니라 transition 으로 한다(중간에 되돌릴 수 있다). `transition-property` 에 바뀌는 속성만 적고 `all` 을 쓰지 않는다.
4. 누른 버튼은 150ms `ease-out` 으로 0.96배로 줄어든다. 비활성 버튼은 줄지 않는다.
5. 입력, 행 hover, 탭 전환처럼 자주 하는 조작은 즉시 반응하거나 `opacity`·`background-color` 만 150ms 이하로 바꾼다. 큰 움직임은 첫 로드, 성공, 빈 상태처럼 드문 순간에만 쓴다.
6. 나갈 때는 들어올 때보다 짧고 작게 움직인다(150ms, 12px 이내). 처음 렌더할 때 기본 상태를 애니메이션으로 띄우지 않는다.
7. 움직임이 상태를 알리는 유일한 수단이 아니다. 움직임이 끝난 뒤에도 색·아이콘·라벨이 남는다.
8. hover 효과는 `@media (hover: hover)` 안에 둔다.
9. 스크롤되는 대화창·서랍·메뉴에 `overscroll-behavior: contain` 을 둔다.
10. 아이콘 선 굵기는 옆 글자 굵기를 따른다(굵기 400 에 1.5px, 700 에 2.5px). 한 화면에 아이콘 세트는 하나다.
11. 테마를 바꿀 때는 전환 효과를 잠시 끈다.

### 4.8 §7 상태와 즉시 차단 항목
1. 화면과 컴포넌트마다 해당하는 상태를 모두 만든다: 기본, hover, focus, 눌림, 비활성, 로딩, 빈 상태, 오류, 좁은 폭(320px), 긴 글(긴 이름, 번역으로 늘어난 라벨).
2. designer 는 이 상태를 시안에 넣는다. director 는 디자인 시스템 컴포넌트마다 상태별 미리보기를 둔다.
3. developer 는 구현한 상태를 실제로 렌더해 확인한다. 프로젝트에 상태 미리보기 도구(Storybook 등)나 E2E 도구가 있으면 그것을 쓴다. 없으면 임시 확인 페이지를 만들어 상태마다 데이터를 바꿔 보고, 확인한 뒤 지운다(커밋하지 않는다). 추적 파일(라우트 등록 등)을 고쳐 임시 페이지를 연결했다면 확인 뒤 되돌린다. 리포트에 확인한 상태, 확인 방법(명령·화면), 확인하지 못한 상태와 이유를 적는다.
4. 삭제처럼 되돌리기 어려운 동작에는 확인 단계, 되돌리기, 다른 동작과 구별되는 표시(위험 색·떨어진 자리) 중 하나 이상을 둔다.
5. 오류 상태는 무엇이 잘못됐는지와 사용자가 할 수 있는 일(다시 시도, 입력 고치기, 문의)을 함께 보여 준다. 문구는 `.orchestration/text-rules.md` §3 의 4번을 따른다.

§7 다음, "자동 검사" 앞에 새 절을 둔다. 항목은 `review-design.md` 10번 P1 목록과 같은 문장이다(테스트가 같음을 확인한다). 첫머리 리포트 소절 설명의 §2–§6 줄에는 "아래 "즉시 차단 항목"은 예외가 인정되지 않는다"를 덧붙인다.

```

아래 항목이 이 태스크에서 새로 생기거나 회귀하면 리포트에 예외를 적었어도 Codex 리뷰는 P1(REQUEST_CHANGES)로 판정한다.
- 접근 가능한 이름이 없는 컨트롤
- 키보드로 닿는데 포커스 표시가 없는 컨트롤, 포인터로만 되는 조작
```

### 4.9 자동 검사 절
지금 "자동 검사" 절을 다음으로 바꾼다.
- `orch review` 는 Codex 를 부르기 전에 태스크가 바꾼 파일에서 다음 의심 위치를 찾아 리뷰 프롬프트에 넣는다. 정당한 쓰임이 있으므로 자동 불합격은 아니다. 나머지는 리뷰어가 화면과 코드를 직접 보고 판단한다.
  - §1 의 1번(이모지), 2번(왼쪽 줄 강조), 3번(파랑·보라 그라디언트)
  - 지운 줄에서 줄어든 접근성·글자 신호(접근 가능한 이름, 포커스, 동작 줄이기, 대체 텍스트, 라벨 연결, `lang`, `keep-all`, `tabular-nums`)
  - 추가한 줄의 확대 막기(`user-scalable=no`·`maximum-scale=1`)와 `focus-visible` 없는 포커스 제거(`outline: none`)

## 6. 리뷰 방식 (`templates/review-design.md`)

`review-prompt.md` 의 기준 1–4 다음에 붙는다. 번호를 이어 쓴다.

```
## 디자인·UI 기준
5. UI 를 바꾼 태스크면 `.orchestration/design-rules.md` 를 읽고 바뀐 화면·코드가 지키는지 본다. §1 금지 목록(이전 버전 프로젝트는 번호 목록 전체) 위반 중 이 태스크가 만든 것(`(새로 생김)`·`(회귀)`)은 REQUEST_CHANGES 사유다. 워커 리포트 마지막 라운드의 `### 디자인 점검`(이전 버전 프로젝트는 `### 금지 목록 점검`)이 실제와 맞는지도 본다.
6. (지금 6번 그대로)
7. 이 태스크가 만든 문제만 지적한다. 디자인 지적은 문제 앞에 `(새로 생김)`·`(회귀)`·`(기존)` 중 하나를 붙인다(예: `- [P1] src/Dialog.tsx:42 — (회귀) 닫기 아이콘 버튼의 aria-label 을 지웠다. 되살린다.`). 위치가 아니라 원인으로 가른다. 바뀐 토큰·공통 컴포넌트 때문에 손대지 않은 화면에 생긴 문제도 이 태스크의 것이다. 토큰이나 공통 컴포넌트를 바꿨으면 그것을 쓰는 화면을 5곳까지 보고, 보지 않은 곳의 수를 `## 직접 확인한 것` 에 적는다. `(기존)` 은 P3 로 3개까지만 적는다.
8. diff 의 지운 줄(`-`)을 읽는다. 접근 가능한 이름·설명(`aria-*`, `alt`, `<label>`), 포커스 표시, `prefers-reduced-motion`, `lang`, 한글 줄바꿈(`keep-all`), 고정폭 숫자, `div` 로 바뀐 `<button>`·`<a>`, 리터럴 값이나 더 옅은 토큰으로 바뀐 색 토큰, 지운 사용자 문구를 찾는다. 같은 변경 안에 대체가 있으면 지적하지 않는다: 보이는 글자를 가리키는 `aria-labelledby`, 같은 `:focus-visible` 의 box-shadow 링, 네이티브 요소로 바뀌어 필요 없어진 `role`·`tabindex`, 값이 같은 토큰, 번역 파일로 옮긴 문구. 대체가 없으면 `(회귀)` 다.
9. 빠진 상태를 찾는다. 새 변형·크기·테마가 hover·focus·눌림·비활성·로딩·선택 중 일부에만 적용됐는가. 새 컴포넌트에 빈 상태·로딩·오류·비활성·좁은 폭이 없는가. 새 컨트롤이 같은 종류의 이웃 화면에는 빠졌는가.
10. 디자인 지적의 심각도:
   - P1: §1 위반과 아래 즉시 차단 항목 중 `(새로 생김)`·`(회귀)` 인 것. 화면이 사소해도 낮추지 않는다.
     - 접근 가능한 이름이 없는 컨트롤
     - 키보드로 닿는데 포커스 표시가 없는 컨트롤, 포인터로만 되는 조작

     - 320px 폭이나 200% 확대에서 잘리거나 겹치거나 닿을 수 없는 내용·컨트롤
     - 기준에 못 미치는 본문·컨트롤 글자 대비
     - 색만으로 전하는 상태·뜻, 뜻과 반대로 쓴 의미 색(위험 색을 일반 동작에)
     - 확인·되돌리기·구별되는 표시가 없는 삭제류 동작
     - 전체를 볼 방법이 없는 잘린 내용, 단서 없이 스크롤 끝이나 접힘 뒤에 숨은 내용·컨트롤
     - 복구 방법을 알려 주지 않는 오류
     - 움직임으로만 알리는 상태 변화
     즉시 차단 항목은 리포트에 예외를 적었어도 P1 이다. 그 밖의 §2–§7 항목은 `### 디자인 점검` 에 적은 예외의 근거가 타당하면 지적하지 않는다.
   - P2: 그 밖의 §2–§7 위반(`(새로 생김)`·`(회귀)`). § 제목이 없는 이전 버전 규칙 파일이면 P2 는 적지 않고 §1 과 즉시 차단 항목만 본다.
   - P3: 사용 영향이 작은 다듬기, `(기존)`(§1 위반 포함).
   같은 등급 안에서는 영향 범위가 넓은 것(토큰·공통 컴포넌트)을 먼저 적는다. 원인이 같은 문제는 지적 하나에 위치를 모은다. 디자인 지적은 15개까지 적고, 채우려고 늘리지 않는다.
11. 고칠 방향은 되는 것 중 가장 앞의 것을 적는다: 지우기(여백으로 될 구분선, 잦은 조작의 애니메이션, 네이티브 요소로 필요 없어진 ARIA) → 플랫폼 기본(네이티브 요소·컨트롤, 브라우저 포커스 링) → 기존 토큰·간격·컴포넌트 재사용 → 값 교정(design-rules 가 정한 값) → 새로 추가. 새 토큰·컴포넌트가 필요하면 designer 는 `### 시스템 추가 제안`, developer 는 ask 로 넘기라고 적는다. 지우기로 고칠 것을 이 변경이 더했으면 그것도 지적이다.
12. 지적마다 파일:줄과 지금 코드를 붙인다. 대비는 토큰·색 값으로 계산할 수 있으면 계산해 색 쌍, 측정값, 기준과 함께 지적한다. 렌더해야 알 수 있는 문제(대비, 잘림, 움직임)는 실행해 확인하고 명령과 결과를 `## 직접 확인한 것` 에 적는다. 확인하지 못했으면 지적하지 않고 "확인 못 함"으로 적는다. 코드만으로 분명한 문제(`aria-label` 이 없는 아이콘 버튼 등)는 렌더 없이 지적한다.
13. 밀도·모서리·말투처럼 시스템이 일관되게 정한 취향은 지적하지 않는다. 즉시 차단 항목은 시스템이 정했어도 지적한다.

{design_lint}
```

- 6번 문장과 붙는 조건(`design_section()`: 직무가 `DESIGN_ROLES` 이고 config 에 director 직무가 있을 때)은 바꾸지 않는다.
- 리뷰 파일 형식(`review-prompt.md`)은 바꾸지 않는다. `(새로 생김)` 등은 지적 줄의 "문제" 앞에 붙는다: `- [P1] src/Dialog.tsx:42 — (회귀) 닫기 아이콘 버튼의 aria-label 을 지웠다. 되살린다.`

## 7. 자동 검사

### 7.1 diff 읽기 공유 (`lib/orch/textlint.py`)
- `added_lines(root, shas, rel) -> set[str] | None` 의 diff 읽기를 `diff_lines(root, shas, rel) -> tuple[list[str], list[str]] | None` 로 일반화한다. 돌려주는 값은 (추가한 줄 목록, 지운 줄 목록)이고, 같은 줄이 여러 번이면 그 수만큼 들어 있다. git 오류면 None.
- `added_lines` 는 `diff_lines` 의 추가한 줄을 집합으로 바꿔 돌려준다. 문구 검사의 동작은 바뀌지 않는다.
- 두 함수는 git 호출 위치가 같은 모듈에 있도록 `textlint.py` 에 둔다. 새 모듈이 `textlint.diff_lines` 를 가져다 쓴다.

### 7.2 새 모듈 (`lib/orch/designdiff.py`)
`design_diff_lint(root, files, shas) -> list[str]`: 태스크 커밋 diff 에서 디자인 회귀·차단 신호의 의심 위치를 찾는다.

- 대상 파일: `files` 중 확장자가 `lint.LINT_SUFFIXES` 이거나 `.dart` `.swift` `.kt` `.xml` 이고, `lint.LINT_EXCLUDE` 에 걸리지 않는 것. `.md` 는 뺀다(디자인 시스템 문서 같은 설명 글이 신호 낱말을 담는다).
- **지운 줄 검사**: 두 단계로 한다. 먼저 대상 파일마다 (파일, 추가한 줄, 지운 줄)을 모은다. 신호마다 태스크 전체(대상 파일 전부)의 지운 일치 수 합에서 추가한 일치 수 합을 뺀 순감소를 구한다. 그 파일의 줄어든 수가 0보다 크고 그 신호의 태스크 전체 순감소도 0보다 클 때만 그 파일 항목을 알린다(n 은 그 파일의 줄어든 수). 같은 속성을 옮기거나 줄만 바꾼 경우, 파일 이동·컴포넌트 추출처럼 다른 파일로 옮긴 경우는 순감소가 0 이하라 걸러진다. 파일이 지금 없어도(삭제) 지운 줄 검사는 한다.
  - 접근 가능한 이름: `aria-label`(뒤에 `ledby` 가 붙지 않은 것), `aria-labelledby`, `aria-describedby`, `aria-live`, `role=`, `alt=`(속성 값이 오는 꼴: 따옴표나 JSX 중괄호가 뒤따르고 앞이 `.`·`$`·`-`·낱말 글자가 아닌 것. `const role = user.role` 같은 변수는 세지 않는다), `<label`, `htmlFor`
  - 포커스: `:focus-visible`, `:focus`(뒤에 `-visible`·`-within` 이 붙지 않은 것), `focus-visible:`, `focus:`(Tailwind. 콜론 바로 뒤에 낱말 글자·`!`·`[` 가 올 때만이라 JS 객체 `focus: {` 는 세지 않는다), `.focus(`, `tabindex`·`tabIndex`
  - 동작 줄이기·대비 설정: `prefers-reduced-motion`, `motion-reduce:`, `motion-safe:`(`focus:` 와 같은 조건), `useReducedMotion`, `prefers-contrast`
  - 언어: `lang=`(`role=`·`alt=` 와 같은 꼴)
  - 한글 줄바꿈: `keep-all`, `break-keep`(Tailwind)
  - 고정폭 숫자: `tabular-nums`
  - 앱: `semanticsLabel`, `semanticLabel`, `Semantics(`, `accessibilityLabel`, `accessibilityHint`, `contentDescription`, `accessibilityReduceMotion`, `isReduceMotionEnabled`, `disableAnimations`
  - 출력: `{rel}: 지운 줄에서 {신호 이름} {n}개가 줄었다(대체가 있는지 확인)`. 신호 이름은 위 묶음 이름이 아니라 개별 신호(`aria-label`, `keep-all` 등)다.
- **추가한 줄 검사**: 지금 파일의 줄 중 이 태스크가 추가한 줄(`diff_lines` 의 추가한 줄 집합에서 태스크가 지운 줄(대상 파일 전부)과 내용이 같은 줄을 뺀 것)을 본다. 옮기기만 한 줄은 추가로 보지 않는다. 줄 번호는 지금 파일 기준이다.
  - 확대 막기: `user-scalable\s*=\s*(no|0)`, `maximum-scale\s*=\s*1`(뒤에 숫자·점이 이어지지 않고, `1.0` 도 포함), Next.js `viewport` 객체의 `userScalable: false`·`maximumScale: 1` → `{rel}:{line}: 확대 막기({조각})`
  - 포커스 제거: `outline\s*:\s*(none|0|0px)`·`outline-style\s*:\s*none`(따옴표 허용, 뒤에 숫자·점이 이어지지 않는 것), Tailwind `outline-none`·`outline-hidden`(v4) → 지금 파일 전체에 `focus-visible` 도, `focus:outline-none`·`focus:ring-0`·`focus:shadow-none`·`focus:ring-transparent` 가 아닌 Tailwind `focus:` 클래스(`focus:ring-2`, `dark:focus:ring-2`, `focus:!ring-2` 등)도 없을 때만 `{rel}:{line}: 포커스 표시 제거({조각}, 파일에 focus-visible 없음)`. `:focus` 셀렉터는 대체로 보지 않는다(`:focus { outline: none }` 이 바로 찾을 대상이다).
  - 조각은 일치한 곳부터 줄 끝까지를 `lint.snippet` 으로 줄인 것이다.
- git 오류(`diff_lines` 가 None)인 파일, 1MB 를 넘거나 UTF-8 이 아닌 파일의 추가한 줄 검사는 건너뛴다.
- 결과 순서: 파일 순서대로, 파일 안에서는 지운 줄 검사(신호 목록 순) 다음 추가한 줄 검사(줄 번호 순).
- 상한을 걸지 않는다. 상한은 부르는 쪽(`review.design_section`)이 건다.

### 7.3 리뷰 프롬프트 연결 (`lib/orch/review.py`)
- `design_section(p, cfg, role, files, shas)` 로 `shas` 를 받는다. `compose_prompt` 가 커밋 SHA 목록을 넘긴다.
- 목록은 `design_diff_lint(root, files, shas)` 결과를 먼저, `lint.design_findings(root, files)`(상한 없는 내용 검사) 결과를 뒤에 이어 붙인 뒤 `lint.cap` 으로 50건(`lint.MAX_FINDINGS`)과 "… 외 N건"으로 자른다. `lint.design_lint` 는 `cap(design_findings(...))` 로 남겨 기존 호출과 테스트를 유지한다.
- 두 검사는 각각 예외를 잡는다. 실패한 검사는 "자동 검사 실패: {예외 이름}: {메시지}" 한 줄(200자 이내, `text_section` 과 같은 형식)로 바뀌고 다른 검사와 리뷰는 계속된다.

## 8. 업그레이드

- 셋업(scaffold)은 있는 파일을 덮어쓰지 않는다. 0.5.1 이하로 만든 프로젝트는 예전 `.orchestration/design-rules.md` 와 `.orchestration/roles/*.md` 를 그대로 쓴다.

## 10. 테스트

  - 지운 줄에서 `aria-label` 이 줄면 알리고, 같은 수를 다시 넣으면(옮김·줄 바꿈) 알리지 않는다.

  - 대상 확장자가 아닌 파일, 제외 경로, git 오류 파일을 건너뛴다. 지운 파일은 지운 줄 검사만 한다.

  - director·designer·developer 직무 문서가 `### 디자인 점검` 을 요구하고 `### 금지 목록 점검` 을 쓰지 않는다.

## 12. 범위 밖

- better-writing 의 문구 규칙("확인 창보다 되돌리기" 등)을 text-rules 에 더하기. 되돌리기는 즉시 차단 항목으로만 다룬다.
- explain-interface·teardown·variant 스킬.
- 원본 플러그인 설치 안내.
- 토큰을 리터럴로 바꾼 곳, `<button>` 을 `div` 로 바꾼 곳의 자동 검사. Codex 가 지운 줄을 읽어 판단한다.
- orch 가 화면을 직접 렌더하는 검사.

## 13. 실환경 확인

병합 전에 사용자 승인을 받고 작은 UI 시험 프로젝트에서 확인한다.

- director·designer·developer 리포트에 `### 디자인 점검` 이 있고, developer 리포트가 §7 의 확인한 상태와 방법을 적는다.
- Codex 디자인 지적에 `(새로 생김)`·`(회귀)`·`(기존)` 이 붙고, 즉시 차단 항목이 P1 이다.
- 자동 검사 결과가 리뷰 프롬프트에 들어간다. 가능하면 `aria-label` 을 지우는 수정 라운드로 지운 줄 검사와 `(회귀)` 판정을 본다.
